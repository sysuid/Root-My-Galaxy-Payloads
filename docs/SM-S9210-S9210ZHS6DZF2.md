## 4. Physical load address (Qualcomm)

This is a Qualcomm device, so the Exynos `sboot.bin` procedure does not apply.
The kernel physical load is the Qualcomm ABL result
`memory_base + ARM64 load constant + text_offset`. The e1q `vendor_boot.img`
contains 22 DTBs whose `/memory` layout anchors the lowest reserved DDR region
as `gunyah_hyp_region@80000000` (with `cpusys_vm_region@80e00000`,
`tags_region@81200000`), fixing the memory base at `0x80000000`. With
`text_offset == 0` and the ARM64 `0x00080000` load constant:

```c
#define P0_PHYS_OFFSET      0x80000000ULL
#define P0_KERNEL_PHYS_LOAD 0x80080000ULL
```

This matches the device-validated S928U1/S928U (e3q) record, which is the
same Snapdragon 8 Gen 3 / android14-6.1 kernel, and differs from the Exynos
`sboot` value `0x80000000` and the newer S25U Qualcomm value `0xa8000000`.

## 5. Slide data and P0 fingerprints

### Trace event ID

The DZF2 ftrace-event section begins at `0x021ff2b0`
(`__start_ftrace_events`) and `__event_sched_blocked_reason` is at
`0x021ff560`; the difference `0x2b0` is 86 eight-byte entries. The Android 6.1
dynamic event base is 20, so the runtime event ID is `20 + 86 = 106`:

```c
#define SLIDE_TRACEFS_EVENT_ID 106
```

### Worker caller offset

Disassembly of `worker_thread` (`0xffffffc0080db100`) shows the idle-worker
blocking call `bl schedule` at `0xffffffc0080db19c`; the saved return/wchan
address is the following instruction:

```c
#define SLIDE_TRACEFS_WORKER_CALLER_OFF 0x000db1a0ULL
```

### pselect word shift and skb bias

The three-qword pselect shift and the `-0x1000` skb fragment bias are the same
as the validated e3q kernel:

```c
#define SLIDE_PSELECT_WORD_SHIFT 3
#define SKB_DATA_DELTA (-0x1000LL)
```

### P0 fingerprints

`p0_fingerprint.h` was generated from this exact raw Image at probe offset
`0x1f0000` with 32 candidate slide rows. Each row `S` was re-verified by
reading back the eight little-endian qwords at Image offsets
`(0x1f0000 − S) + {0x000, 0x200, ..., 0xe00}`; all 32 rows match the raw
Image byte-for-byte (256 source qwords total).

## 10. Cleanup and retention (PORTING.md step 9)

The raw `kernel`, `vmlinux.elf`, `vmlinux.btf`, `kernel.config`, and the
generated headers are retained as the provenance set; the multi-gigabyte
firmware ZIP and AP/BL/CP archives are not tracked in the repository. Hardware
execution remains a separate validation step: verify the model, full kernel
release, and artifact hash, then collect the physical-P0 oracle, slide-
discovery, and overwrite-path logs.
