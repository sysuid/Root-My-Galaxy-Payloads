## 4. Physical load address (Qualcomm)

This is a Qualcomm device, so the Exynos `sboot.bin` procedure does not apply.
The kernel physical load is the Qualcomm ABL result
`memory_base + ARM64 load constant + text_offset`. The e1q `vendor_boot.img`
contains 22 DTBs whose `/memory` layout anchors the lowest reserved DDR region
as `gunyah_hyp_region@80000000` (with `cpusys_vm_region@80e00000`,
`tags_region@81200000`), fixing the memory base at `0x80000000`. With
`text_offset == 0` and the ARM64 `0x00080000` load constant:

```c
#define P0_PHYS_OFFSET      0x80000000ULL
#define P0_KERNEL_PHYS_LOAD 0x80080000ULL
```

This matches the device-validated S928U1/S928U (e3q) record, which is the
same Snapdragon 8 Gen 3 / android14-6.1 kernel, and differs from the Exynos
`sboot` value `0x80000000` and the newer S25U Qualcomm value `0xa8000000`.

## 5. Slide data and P0 fingerprints

### Trace event ID

The DZF2 ftrace-event section begins at `0x021ff2b0`
(`__start_ftrace_events`) and `__event_sched_blocked_reason` is at
`0x021ff560`; the difference `0x2b0` is 86 eight-byte entries. The Android 6.1
dynamic event base is 20, so the runtime event ID is `20 + 86 = 106`:

```c
#define SLIDE_TRACEFS_EVENT_ID 106
```

### Worker caller offset

Disassembly of `worker_thread` (`0xffffffc0080db100`) shows the idle-worker
blocking call `bl schedule` at `0xffffffc0080db19c`; the saved return/wchan
address is the following instruction:

```c
#define SLIDE_TRACEFS_WORKER_CALLER_OFF 0x000db1a0ULL
```

### pselect word shift and skb bias

The three-qword pselect shift and the `-0x1000` skb fragment bias are the same
as the validated e3q kernel:

```c
#define SLIDE_PSELECT_WORD_SHIFT 3
#define SKB_DATA_DELTA (-0x1000LL)
```

### P0 fingerprints

`p0_fingerprint.h` was generated from this exact raw Image at probe offset
`0x1f0000` with 32 candidate slide rows. Each row `S` was re-verified by
reading back the eight little-endian qwords at Image offsets
`(0x1f0000 − S) + {0x000, 0x200, ..., 0xe00}`; all 32 rows match the raw
Image byte-for-byte (256 source qwords total).

## 6. Corrections found during the audit

Three constants in the original profile were wrong and were corrected against
the recovered ELF/disassembly and the validated e3q reference:

| Constant | Was | Now | Evidence |
| --- | --- | --- | --- |
| `P0_KERNEL_PHYS_LOAD` | `0x80000000` | `0x80080000` | Qualcomm ABL `memory_base + 0x80000`; e1q DTB `gunyah_hyp_region@80000000`; e3q device-validated |
| `SLIDE_RANDOM_TABLE_BOOT_ID_DATA_PTR_OFF` | `0x023762e8` | `0x023762f0` | The boot_id ctl-table `.data` slot is `random_table + 0x108`; `0x23762e8` is the `procname` field |
| `SLIDE_TRACEFS_WORKER_CALLER_OFF` | `0x000dbd9c` | `0x000db1a0` | `bl schedule` at `0x...db19c`, saved return `0x...db1a0` in this kernel |
| `p0_fingerprints[]` row ordering | reversed to mirror e3q | generator-forward (`row S = X[(0x1f0000 − S)]`) | Re-audited byte-for-byte against the raw Image: `X[0x1f0000] = a9017fff...`, `X[0x000000] = 1477694e...`; the generator-forward table matches all 32 rows, the e3q-mirrored orientation matches 0/32 |

The `0x000dbd9c` and `0x80000000` values were the Exynos S24 FE (`essi`) values
and had been carried over; the boot-ID pointer was an off-by-8 from
`random_table + 0x100` (the `procname` slot). All other offsets in `target.h`
were confirmed exact against the recovered `vmlinux.elf`.

## 8. KernelSU late-load (PORTING.md step 7)

Status: **COMPLETE for target-specific build and static compatibility audit**.

The e1q kernel is build `33419968` on `android14-6.1` — the same kernel build
as the device-validated Snapdragon E3Q (`S928USQS6DZF2`), differing only in
the release-string model suffix (`abS9210ZHS6DZF2` vs `abS928USQS6DZF2`). All
recovered symbols and BTF layouts are identical. The target enables
`CONFIG_MODVERSIONS=y`, `CONFIG_TRIM_UNUSED_KSYMS=y`, `CONFIG_MODULE_SIG=y`,
`CONFIG_RKP=y`, `CONFIG_KDP=y`/`CONFIG_KDP_CRED=y`, with no
`CONFIG_MODULE_FORCE_LOAD`, so the E3Q procedure applies directly:

1. **Source**: KernelSU tag `v3.2.5` (commit
   `b0bc817b4e966aa6aa830834eaf6ef765d821d40`), patched with
   `kernelsu/patches/KernelSU-v3.2.5-samsung-kdp-rkp-defex.patch`.
2. **Build**: DDK image `ghcr.io/ylarod/ddk-min:android14-6.1-20260313` (Clang
   17.0.2, `r487747c`). Replace the generated `UTS_RELEASE` and
   `include/config/kernel.release` with the exact e1q release
   `6.1.145-android14-11-33419968-abS9210ZHS6DZF2` (the DDK default
   `6.1.166-dirty` would be rejected because `CONFIG_MODULE_FORCE_LOAD=n`).
   Build with `CONFIG_KSU=m`, `CONFIG_KSU_SAMSUNG_KDP=y`,
   `CONFIG_KSU_SAMSUNG_RKP=y`, `CONFIG_KSU_SAMSUNG_DEFEX=y`. The built module
   reports the exact target vermagic:

   ```text
   vermagic: 6.1.145-android14-11-33419968-abS9210ZHS6DZF2 SMP preempt mod_unload modversions aarch64
   ```

3. **Symbol audit**: `kernel/check_symbol` exits 0 against the recovered
   `vmlinux.elf`. Because `CONFIG_TRIM_UNUSED_KSYMS=y`, the module keeps a
   zero-length `__versions` section and is loaded through KernelSU's
   kallsyms-based manual relocation. The repository audit
   (`audit_module_against_target.py --manual-relocation`) reports:

   ```text
   undefined symbols: 209
   module version entries: 0            (zero-length __versions, manual relocation)
   missing from target symbol table: 0
   symbols resolved from kallsyms rather than target exports: 73
   undefined symbols intentionally without module CRC: 209
   target CRC mismatches: 0
   ```

   All undefined imports are present in the recovered ELF.
4. **Package**: `llvm-strip -d` the KO, place it in the
   `android14-6.1_kernelsu.ko` asset slot, and rebuild `ksud` for
   `aarch64-linux-android` with NDK r29. Publish the pair as
   `kernelsu/android14-6.1_kernelsu-e1q-S9210ZHS6DZF2-kdp.ko` and
   `kernelsu/ksud-e1q-S9210ZHS6DZF2-kdp` together.
